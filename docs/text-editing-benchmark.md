# 본문 직접 편집과 문장 단위 복원 — 선행 조사

2026-10-09. 공식 제품 문서와 현재 코드에 근거한 기능 비교다. 경쟁 제품을 설치해 직접 성능을 측정한 결과는 아니다.

## 비교한 편집 방식

| 제품                                                                                                        | 편집 단위와 입력 방식                                                                                         | Paperkit에 적용할 점                                                              |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| [Adobe Acrobat](https://helpx.adobe.com/acrobat/using/edit-text-pdfs1.html)                                 | 편집 모드에서 텍스트 상자를 선택하고 본문을 수정. 상자 내부에서 내용 재배치, 인접 상자/다음 페이지와는 독립적 | 보기/편집 모드를 분리하고 글자 위치에서 입력. 문서 전체 재배치는 별도 문제로 취급 |

| [Apryse](https://apryse.com/blog/javascript/how-to-edit-text-in-a-pdf-with-javascript)                      | 문단을 선택해 내용/크기 등을 편집하는 콘텐츠 편집 기능                                                        | 선택한 화면 영역과 실제 콘텐츠 변경 대상을 연결해야 함                            |

각 제품의 문단 복원 내부 알고리즘까지 공개된 것은 아니다. 아래 판단 기준은 Paperkit의 설계 제안이다.

## 현재 글자/단어 단위로 보이는 이유

`pdf-core/src/text.rs`는 `page.objects()`의 직접 텍스트 객체마다 ID를 만들고,
`TextPage.tsx`는 각 객체의 경계를 선택 영역으로 사용한다. 한국어/영어에 따라 분할하는 코드는 없다.
따라서 저장 시 글자마다 객체를 만든 PDF는 글자 단위, 단어마다 만든 PDF는 단어 단위로 선택된다.
사용자가 보고한 특정 파일 자체의 객체 수와 좌표는 아직 분석하지 않았으므로 파일별 원인을 확정한 것은 아니다.

PDF의 콘텐츠 저장 순서와 사람이 읽는 논리적 순서는 다를 수 있다.
[PDF Association의 텍스트 추출 설명](https://pdfa.org/what-you-may-be-missing-when-you-search-pdf-documents/)도 이 차이를 설명한다.
단순히 인접 배열 원소를 붙이는 방법은 여러 단, 표, 머리말을 잘못 연결할 수 있다.

## 문장의 특성과 묶기 기준

| 특성                | 필요한 판단                                             | 잘못 묶으면 생기는 문제                     |
| ------------------- | ------------------------------------------------------- | ------------------------------------------- |
| 같은 줄의 글자 조각 | 기준선, 쓰기 방향, 글자 높이, 글자 사이 간격으로 정렬   | 영문 철자 사이에 불필요한 공백 삽입         |
| 한국어 어절         | 기존 공백을 보존하고 실제 단어 간격과 자간을 구분       | 조사/어미 분리, 모든 어절을 붙여 쓰기       |
| 영문 문장부호       | 마침표뿐 아니라 약어, 소수, URL, 인용문 고려            | `Dr. Kim`, `3.14`를 여러 문장으로 잘못 분리 |
| 줄을 넘는 문장      | 같은 단/블록의 들여쓰기, 줄 간격, 문장 종결을 함께 판정 | 한 줄을 완성된 문장으로 오인                |
| 영문 줄끝 하이픈    | 실제 하이픈과 줄바꿈 때문에 생긴 하이픈 구분            | 원문 철자와 검색 문자열 훼손                |
| 혼합 서식           | 문장 안에 폰트·굵기·색상별 run과 원본 객체 매핑 유지    | 강조 부분의 서식 소실                       |
| 다단/표/각주        | 열 경계, 큰 간격, 행·셀 경계에서 묶기 중단              | 서로 다른 열/셀의 문장을 연결               |
| 회전/세로쓰기       | 같은 방향끼리 별도로 좌표 정규화                        | 페이지 순서 및 입력 방향 오류               |
| 스캔/윤곽선         | 텍스트가 없음을 구분                                    | 이미지에 임의 텍스트를 덧씌우는 잘못된 편집 |

문장과 줄, 문단은 다른 단위다. 최소 문장 단위를 지원하려면 **여러 줄에 걸친 한 문장**과
**같은 줄에 있는 여러 문장**을 모두 처리해야 한다. 공백 또는 마침표만으로 나누는 구현은 하지 않는다.

## 제안하는 구현 순서와 완료 기준

1. Rust에서 읽기 순서와 줄/블록 후보를 구성한다. 가능하면 PDF 논리 구조와 문자 좌표를 함께 이용한다.
2. 각 문자 범위를 원본 객체 ID/문자 오프셋/서식 run에 매핑한다. 줌과 무관한 PDF 좌표로 판정한다.
3. 블록 안에서 언어별 문장 경계를 판정한다. 문장 후보에 여러 줄의 선택 사각형을 연결한다.
4. 여러 객체에 걸친 수정은 한 번의 Rust 트랜잭션으로 처리한다. 한 객체에 문장 전체를 쓰고 나머지를 남기는 방식은 금지한다.
5. 기존 문장 영역 내에서만 줄 배치와 run 배분을 계산하고, 누락 글리프·영역 초과·불명확한 읽기 순서는 거절한다.
6. 한 Undo로 전체 문장 변경을 되돌리고, 저장 후 문장/서식/주변 픽셀을 재검증한다.

검증 표본은 영문 글자별 객체, 한글 어절별 객체, 혼합 서식, 두 줄 문장, 한 줄의 두 문장,
약어/소수, 두 단, 표, 회전, 서브셋 폰트를 포함해야 한다. 표본별 기대 문장과 객체 매핑을 먼저 고정한다.
글자/단어 묶기의 성공률과 다른 열/표로 잘못 연결하는 비율을 각각 기록한다.

## 이번에 적용한 범위

- 기본 읽기 전용과 명시적인 ‘편집 사용’ 버튼.
- 오른쪽 속성/내용 패널을 제거하고 선택한 객체 위치에 임시 입력창 배치.
- 입력창은 React UI다. 저장할 때는 기존 Rust `set_text` 경로를 사용하며 흰 사각형/추가 텍스트를 PDF에 저장하지 않는다.
- Ctrl+Enter 적용, Esc로 나가기, 미적용 변경 확인, IME 조합 중 단축키 무시.
- 입력 중 브라우저 대체 폰트가 사용될 수 있으며 적용 후 결과는 PDFium 렌더로 확인한다.

위 목록은 최초 조사 단계의 범위다. 후속 구현은 아래와 개발 체크리스트를 참고한다.
‘편집 사용’은 PDF의 권한 제한이나 글리프 제한을 해제하지 않는다.

## 2026-10-10 문장 복원 구현

`pdf-core/src/layout.rs`에서 실제 문자 배치 경계(loose bounds)와 기준선을 사용해 줄/문단 후보를 구성한다.
약어·소수·URL의 마침표를 고려한 문장 분리 후 원본 객체 ID와 Unicode 문자 범위를 연결한다.
글자 잉크 경계를 자간으로 사용하면 `ll` 사이에 공백이 잘못 생길 수 있어 배치 폭을 사용한다.
실제 DLL 표본에서 PDFium의 객체 문자열 끝에 생성 공백이 붙는 현상을 확인했고,
이를 실제 원본 글리프로 쓰지 않도록 구분한다. 줄끝 하이픈은 추측하여 제거하지 않는다.

문장/문단 선택은 여러 줄의 영역을 함께 강조한다. 여러 객체 수정은 문자 수와 공백 위치를 유지하면서
각 원본 객체의 문자 범위에 분배하고, 모든 검증이 성공한 뒤 한 번만 커밋한다.
한 객체 안의 두 문장을 각각 선택해도 선택 밖 문자열은 유지한다.
혼합 서식은 원본 객체별로 유지하며 글꼴 선택에는 ‘혼합’을 표시한다.
이후 블록 직접 편집 구현은 다음 절을 참고한다.

수평 본문에 한정한 휴리스틱이며 모든 문서의 의미적 문단을 보장하지 않는다.
서로 떨어진 같은 행의 블록은 독립 대상으로 유지하고 실제 겹침만 불확실 표시한다. 경로 선/큰 간격에서는 분리, 회전 및 문자 매핑 불일치는
객체 선택으로 남긴다. 제작 도구별 정확도 측정과 복잡한 표 처리는 아직 남아 있다.

## 블록 직접 편집 구현

문단 외곽을 하나의 블록으로 표시하고 `contenteditable="plaintext-only"`로 직접 입력한다.
[MDN의 contenteditable 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/contenteditable)에 따라
일반 텍스트 붙여넣기와 브라우저 편집 동작을 사용한다. 클릭 커서는
[caretPositionFromPoint](https://developer.mozilla.org/en-US/docs/Web/API/Document/caretPositionFromPoint)를 우선 사용하고 WebView의 이전 API로 대체한다.
입력마다 React가 DOM을 교체하지 않아 선택/조합 중인 텍스트를 유지한다. 실제 Windows IME 및 드래그 수동 검증은 남아 있다.

같은 서식의 완전한 문단은 PDFium 폰트로 글자 전진 폭을 측정해 원래 폭 안에서 줄을 나눈다.
줄 수는 원래 블록의 줄 수를 넘을 수 없으며 폰트·크기·색·변환을 유지한다. 원본 객체들을 제거한 뒤
줄별 실제 텍스트 객체로 바꾸고 저장 바이트를 다시 열어 문자열·속성·주변 픽셀을 검증한다.
화면의 편집 레이어는 UI일 뿐 PDF에 배경 사각형을 추가하지 않는다.
혼합 서식과 부분 객체는 자유 재배치를 적용하지 않고 기존 문자 범위 수정으로 남긴다.

동봉 폰트는 동일한 TTF를 FontFace로 로드하며 기준선과 가로 배율을 보정한다.
시스템 대응 폰트가 필요한 기본 PDF 폰트, 사용자 지정 자간, 회전, 혼합 서식 입력의 화면 일치는 추가 검증 대상이다.

## 스크롤 진단과 수정

기존 목록은 보이는 범위가 바뀔 때마다 새 비동기 루프를 만들었다. 이전 루프의 네이티브 렌더는
취소되지 않아 빠른 스크롤에서 요청이 겹칠 수 있었다. 오류 안내가 생겨 높이가 달라지면
높이를 의존성으로 둔 자동 스크롤이 현재 선택 페이지로 되돌리는 경로도 있었다.

범위 변경 사이에서도 요청 하나만 유지하고 완료 후 최신 범위를 읽도록 수정했다.
자동 이동은 페이지 선택/사이드바 열기에만 적용하며 높이 변화는 스크롤 위치를 바꾸지 않는다.
가상 목록의 브라우저 scroll anchoring도 해제했다. 느린 응답·연속 스크롤·오류 후 높이 변경·접기/열기 회귀 테스트를 추가했다.
실제 사용자가 본 모든 끊김 현상의 원인이 동일하다고 단정하지는 않는다. 큰 PDF의 렌더 자체는 여전히 시간이 걸릴 수 있다.

## 용량 제한 확인

- 열기: 원본 파일 최대 **128 MiB (134,217,728 bytes)**. Rust `render.rs`의 파일 읽기 전/후 검사.
- 편집/저장: 직렬화한 문서 스냅샷 최대 **32 MiB (33,554,432 bytes)**. 원본 파일 크기와 다를 수 있음.
- Undo 보관: 최대 20개, undo 스냅샷 합계 128 MiB. 앱 전체 메모리 상한이라는 의미는 아님.
- 페이지 수 자체의 별도 정책 상한은 현재 없음. 이미지 렌더는 최대 폭 1600px/높이 2200px.

이번 변경에서 용량 제한은 늘리거나 없애지 않았다.

# 편집 영역과 글꼴 전환 추가 조사

Adobe는 원본 글꼴을 사용할 수 없을 때 대체 글꼴을 사용하며 이 때문에 모양이 달라질 수 있다고 설명한다.
[Adobe 글꼴 대체 안내](https://helpx.adobe.com/acrobat/desktop/edit-documents/edit-text-in-pdfs/set-default-font.html).
Paperkit은 임의로 바꾸지 않고 사용자가 선택한 문단을 제공 글꼴로 전환한다. 원본 서브셋 글꼴에 없는 글리프를 강제로 추가하지 않는다.
크기·색·변환이 같고 원본 객체 전체를 포함하는 블록만 지원하며, 새 글꼴의 줄바꿈이 기존 영역을 넘으면 거절한다.
이후 UX 개선으로 글꼴 목록을 먼저 고를 필요 없이 더블 클릭해서 기본 Pretendard로 초안을 입력할 수 있다.
미리보기 안내와 달리 실제 원본 객체는 내용 적용 전에는 변경하지 않는다. 적용 시 글꼴과 내용을 한 번에 검증하고 Undo 한 번으로 되돌린다.

PDF 텍스트 추출의 블록→줄→span 구조는 문단을 복원하는 기반이지만 원래 워드 문단과 같다고 보장하지 않는다.
[PyMuPDF 텍스트 추출 구조](https://pymupdf.readthedocs.io/en/latest/app1.html).
따라서 공백만으로 묶지 않는다. 현재 구현은 주변 기본 줄 간격의 중앙값과 줄 사이 실제 간격,
왼쪽 정렬·첫 줄 들여쓰기, 글자 크기, 짧은 종결 행, 표 경로와 같은 행의 열 분리를 함께 사용한다.
다음 줄이 더 길다는 이유만으로 나누던 조건은 제거했다. 이 임계값은 Paperkit 자체 휴리스틱이며 경쟁 제품의 내부 알고리즘을 재현한 것은 아니다.

편집 모드에서는 선택 전에도 문단 외곽을 점선으로 표시한다. 초록은 현재 편집 경로 사용 가능,
주황은 명시적 글꼴 전환 가능, 회색은 안전하게 편집할 수 없는 영역이다. 초록이라도 혼합 서식은 길이 변경에 제한이 있다.
실제 사용자 문서의 정량적인 문단 검출 정확도와 화면 일치는 아직 검증하지 않았다.
